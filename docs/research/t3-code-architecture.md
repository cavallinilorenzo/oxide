# T3 Code architecture and Oxide MVP scope

**Source snapshot:** Oxide pins `references/t3code` to `680152e27b2a961686389ca69a1557cbb2c55f08` (official [`pingdotgg/t3code`](https://github.com/pingdotgg/t3code/tree/680152e27b2a961686389ca69a1557cbb2c55f08)). Local paths below refer to that revision. GitHub API details were checked against current GitHub REST documentation on 2026-10-21.

## Findings

### Process split and boundary

T3 is a monorepo with a local **Node server** (`apps/server`), **React web client** (`apps/web`), and **Electron desktop shell** (`apps/desktop`); there is also a mobile client. The server owns workspace files, agent/provider processes, Git, terminals, and durable state. Web, desktop renderer, and mobile call the server through the shared typed RPC contract in `packages/contracts`; clients receive scoped snapshots/subscriptions rather than owning workspace state. Electron packages/launches the same server runtime (`apps/desktop/src/backend/DesktopBackendConfiguration.ts`). The architecture docs explain why this boundary also supports remote environments: [internals/overview.md](../../references/t3code/docs/internals/overview.md), [contracts/rpc.ts](../../references/t3code/packages/contracts/src/rpc.ts).

### Threads, event flow, and persistence

Thread commands enter the server orchestrator, which decides domain events. Provider and filesystem I/O are queued as effects: `EventSink` commits events, projections, command receipts, and effect-outbox rows transactionally; only after commit are events published and the worker runs effects. Provider output is normalized to events and fed back into orchestration. This is a durable event-sourced state machine, not a request handler that directly mutates a thread and calls an agent. See [Orchestrator.ts](../../references/t3code/apps/server/src/orchestration-v2/Orchestrator.ts), [EventSink.ts](../../references/t3code/apps/server/src/orchestration-v2/EventSink.ts), [EffectWorker.ts](../../references/t3code/apps/server/src/orchestration-v2/EffectWorker.ts), [ProviderEventIngestor.ts](../../references/t3code/apps/server/src/orchestration-v2/ProviderEventIngestor.ts), and [overview.md](../../references/t3code/docs/internals/overview.md).

SQLite stores an append-only event log (`orchestration_events`; V2 migrations add `orchestration_v2_events` plus projections), with materialized read models for projects, threads, runs, messages/items, provider sessions, subagents, checkpoints, pending approvals, PR links, and settings. Command receipts support idempotent retries; an effect outbox supports recovery. `payload_json` is schema-version-sensitive history, so compatibility/migrations are part of the product burden. Initial and V2 schema examples: [001_OrchestrationEvents.ts](../../references/t3code/apps/server/src/persistence/Migrations/001_OrchestrationEvents.ts), [005_Projections.ts](../../references/t3code/apps/server/src/persistence/Migrations/005_Projections.ts), [OrchestrationV2/Foundation.ts](../../references/t3code/apps/server/src/persistence/Migrations/OrchestrationV2/Foundation.ts), [CommandReceiptStore.ts](../../references/t3code/apps/server/src/orchestration-v2/CommandReceiptStore.ts).

### Provider abstraction

`provider-core` defines a per-instance `ProviderDriver` (configuration schema, identity, lifecycle, status/model snapshots) that exposes a normalized `ProviderAdapterV2` runtime: open/resume/ensure thread, start/steer/interrupt turns, runtime requests, snapshots, rollback/fork, and a typed event stream. Driver-specific adapters translate native provider protocols into shared contracts; orchestration acts on normalized events and capabilities. This is powerful but an extensive seam: multiple provider protocols, auth, model catalogs, session recovery, permissions, native capabilities and version differences live behind it. See [driver.ts](../../references/t3code/packages/provider-core/src/server/driver.ts), [ProviderAdapter.ts](../../references/t3code/packages/provider-core/src/server/ProviderAdapter.ts), and [providers.md](../../references/t3code/docs/internals/providers.md).

### Git, worktrees, PRs, checks, and “changes in this Thread”

The VCS driver abstracts Git operations, including branch/ref operations, worktree creation/removal, status, and checkpoint operations. Git-specific workflows sit in server services; per-thread worktrees are prepared during thread launch and allow concurrent work without sharing mutable files. Checkpoints use hidden Git refs, so turn diffs compare captured before/after states without adding commits. “Changes in this Thread” are therefore computed from checkpoint refs tied to a thread/run, not inferred from current branch status: [GitWorkflowService.ts](../../references/t3code/apps/server/src/git/GitWorkflowService.ts), [GitManager.ts](../../references/t3code/apps/server/src/git/GitManager.ts), [ThreadLaunchService.ts](../../references/t3code/apps/server/src/orchestration-v2/ThreadLaunchService.ts), [CheckpointStore.ts](../../references/t3code/apps/server/src/checkpointing/CheckpointStore.ts), [CheckpointDiffQuery.ts](../../references/t3code/apps/server/src/checkpointing/CheckpointDiffQuery.ts).

Hosting services are pluggable too: `source-control-core` defines provider capabilities, while GitHub has a dedicated implementation. GitHub PR listing, review, mutation, merge and check data use authenticated REST/GraphQL clients, caching/rate-limit policies, and conditional check revalidation; local Git commands remain separate. GitHub CLI (`gh`) is also used for auth discovery/status and some GitHub-aware local workflows, so the answer is **both**, not “all via gh” or “all via API.” See [source-control-core](../../references/t3code/packages/source-control-core/src/server/driver.ts), [GitHubRest.ts](../../references/t3code/packages/source-control-github/src/server/GitHubRest.ts), [GitHubPullRequestApi.ts](../../references/t3code/packages/source-control-github/src/server/GitHubPullRequestApi.ts), [GitHubSourceControlProvider.ts](../../references/t3code/packages/source-control-github/src/server/GitHubSourceControlProvider.ts), [gitHubConditionalChecks.ts](../../references/t3code/packages/source-control-github/src/server/gitHubConditionalChecks.ts), and [PullRequestSyncReactor.ts](../../references/t3code/apps/server/src/orchestration-v2/PullRequestSyncReactor.ts). Current upstream API facts: GitHub documents REST endpoints for [pull request operations including merge](https://docs.github.com/en/rest/pulls), [check runs](https://docs.github.com/en/rest/checks/runs?apiVersion=2026-03-10), and [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2026-03-10).

### First launch and terminal execution

First-run onboarding is not merely “find Git repos.” The server scans existing agent transcript/session stores, groups candidate working directories, validates real directories, resolves symlinks/identity, excludes worktree/internal paths, detects Git remotes, reconciles already-imported Projects, then offers selected recent histories for import. The client waits for authoritative bootstrap/project/provider evidence before deciding whether to show the first-run wizard. The root may also be bootstrapped from server cwd. See [AgentSessionScanner.ts](../../references/t3code/apps/server/src/project/AgentSessionScanner.ts), [AgentSessionImporter.ts](../../references/t3code/apps/server/src/project/AgentSessionImporter.ts), [projectImport.logic.ts](../../references/t3code/apps/web/src/onboarding/projectImport.logic.ts), [firstRun.logic.ts](../../references/t3code/apps/web/src/onboarding/firstRun.logic.ts), and [ProjectService.ts](../../references/t3code/apps/server/src/project/ProjectService.ts).

Interactive terminals are server-owned `node-pty` processes with per-session state, persisted bounded scrollback, attach/output streams, resize, cwd/environment selection, process discovery, and termination. Native PTY loading/spawn-helper management is platform-aware. This is a distinct subsystem from provider shell/tool calls. See [Manager.ts](../../references/t3code/apps/server/src/terminal/Manager.ts) and [NodePtyAdapter.ts](../../references/t3code/apps/server/src/terminal/NodePtyAdapter.ts).

## MVP mapping for Oxide

The current Oxide glossary defines Project, Thread, Provider, and Surface, but the repo does not yet specify a final persistence or hosting design ([GLOSSARY.md](../../GLOSSARY.md)); the mappings below are recommendations/inference, not verified Oxide commitments.

| T3 capability | Oxide MVP mapping |
|---|---|
| Local server plus clients over RPC | Start with one local application process and one UI surface. Keep filesystem/provider execution on the owning machine behind a small internal interface; defer remote environments and multi-client compatibility. |
| Event-sourced orchestration + outbox + projections | Use a compact persisted Thread/run/message state and append-only activity/events only where replay/recovery pays off. Defer generic event sourcing, subagent topology, retries/receipts/outbox until concrete async recovery needs emerge. Preserve explicit run statuses and provider streaming. |
| Many provider adapters and model/config/auth subsystems | Ship one Provider end-to-end, normalized behind a narrow interface (`start`, stream events, stop, resume if supported). Add additional Provider drivers only when needed. |
| Multi-host source control, PR reviews/stacks/check watches | Keep local Git status and per-Thread diff first. Defer GitHub API integration, PR creation/merge/checks and other hosts. |
| Checkpoint-based per-turn diffs | Capture a baseline and compute Thread change summary against it. If rollback is out of scope, don’t build checkpoint restore, hidden refs, scoped checkpoints, or authored-path heuristics yet. |
| Agent-history discovery/import | Discover Projects through explicit folder open/recent folders; avoid parsing multiple agents’ private session formats for initial launch. |
| Persistent interactive PTYs | Include only if the MVP needs a visible terminal. Otherwise rely on Provider-exposed commands; if included, make PTY server/process ownership explicit and keep shell sessions independent from agent runs. |

### Heavy parts / likely latency costs

**Verified architecture:** this revision contains a very large provider surface, durable event/projection migrations, recovery/reconciliation workers, Git/worktree/checkpoint code, a GitHub GraphQL+REST client, and PTY process management. Those are major implementation and compatibility costs to reproduce. **Inference:** first launch can feel slow because onboarding scans multiple provider-owned transcript stores and performs filesystem/Git identity checks; visible runtime waits can also include asynchronous setup, provider CLI startup/model discovery, worktree preparation, checkpoint capture/diff, and external GitHub requests. The code includes caches, bounded scans/output, coalescers and performance regression tests, but this source review did not benchmark timings, so it cannot rank actual user-perceived latency causes.

## Unknowns and limits

- The reference submodule directory was empty on checkout; I fetched the official repository and inspected the exact pinned commit above. Findings are limited to that commit.
- No Oxide MVP spec beyond the glossary and issue #6 was present, so MVP scope is a recommendation.
- Source review shows the mechanisms, not production load, startup traces or measured bottlenecks. The latency explanation is a hypothesis to validate with profiling.
- Some provider actions may intentionally execute through their native CLI/protocol; the report describes the shared abstraction rather than claiming all providers use one transport.

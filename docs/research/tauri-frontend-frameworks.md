# Tauri v2 frontend choice for Oxide chat

**Ticket:** [#8](https://github.com/cavallinilorenzo/oxide/issues/8)  
**Research date:** 2026-10-21

## Recommendation

Prototype **Svelte 5, Solid, and React** against the same streaming-chat workload. Treat React as the ecosystem and reuse baseline (the ticket identifies it as T3 Code's choice; that codebase is not in this checkout), Solid as the fine-grained-update candidate, and Svelte 5 as the compiler/runes candidate. Keep **Dioxus or Leptos** as a follow-on only if an all-Rust frontend is an explicit product goal.

There is no verified apples-to-apples benchmark here that establishes a fastest framework. Inference: for this UI, controlling update frequency, keeping the DOM bounded with virtualization, and avoiding repeated whole-message markdown/highlight work are likely more consequential than framework choice alone. Measure those behaviors before choosing a winner.

## Comparison

| Option | High-rate stream and render model | Long lists | Bundle, memory, ecosystem, maturity |
|---|---|---|---|
| **Solid** | Fine-grained signals update the DOM locations that read changed values; Solid components run once on initialization. This is a strong fit for frequently changing token text, provided state is split so a token does not invalidate the whole conversation. ([reactivity docs](https://docs.solidjs.com/advanced-concepts/fine-grained-reactivity), [state docs](https://docs.solidjs.com/guides/state-management)) | Official TanStack Virtual adapter. ([framework adapters](https://tanstack.com/virtual/latest/docs/framework)) | JS/TS renderer keeps access to the web ecosystem. No verified Oxide-specific bundle or heap figures. Official Tauri scaffolding includes Solid; Tauri's frontend guide lists Svelte and Leptos explicitly, while the official scaffolder also offers React and Solid. ([scaffolder](https://github.com/tauri-apps/create-tauri-app)) |
| **Svelte 5** | Compiler-generated components plus runes (`$state`, `$derived`) provide reactive state and dependency-based updates. The compiler's output is ordinary JS; claims of inherently faster runtime are not established by this research for Oxide's workload. ([compiler docs](https://svelte.dev/docs/svelte/svelte-compiler), [derived docs](https://svelte.dev/docs/svelte/%24derived)) | Official TanStack Virtual adapter. ([framework adapters](https://tanstack.com/virtual/latest/docs/framework)) | JS/TS library ecosystem; no comparable Oxide bundle/heap data found. Official Tauri frontend setup docs cover Svelte and the official scaffolder has a maintained Svelte template. ([Tauri frontend guide](https://v2.tauri.app/start/frontend/), [scaffolder](https://github.com/tauri-apps/create-tauri-app)) |
| **React** | State updates trigger component renders; React then reconciles and commits DOM changes. `useTransition` can mark non-urgent work as interruptible, but controlled input updates remain synchronous. Split state, memoize expensive subtrees where justified, and coalesce stream updates. ([render and commit](https://react.dev/learn/render-and-commit), [useTransition](https://react.dev/reference/react/useTransition)) | Official TanStack Virtual adapter, including a chat example. ([framework adapters](https://tanstack.com/virtual/latest/docs/framework), [chat example](https://tanstack.com/virtual/latest/docs/framework/react/examples/chat)) | Inference: React's broader ecosystem and the team's existing React knowledge (if available) make it a practical baseline; T3 Code UI reuse is unverified because its source is absent from this checkout. Official Tauri scaffold offers React. ([scaffolder](https://github.com/tauri-apps/create-tauri-app)) |
| **Rust/WASM: Leptos or Dioxus Web** | UI logic can be written in Rust and compiled to WASM, but actual DOM rendering still crosses the WebAssembly/JS/browser boundary. No directly comparable streaming benchmark was found. Dioxus documents JS escape hatches for webview DOM access. ([Dioxus web platform](https://dioxuslabs.com/learn/0.7/guides/platforms/web/), [escape hatches](https://dioxuslabs.com/learn/0.7/essentials/ui/escape/)) | The common TanStack Virtual framework adapters do not include Leptos or Dioxus; custom interop or a Rust-native virtualizer needs evaluation. ([adapters](https://tanstack.com/virtual/latest/docs/framework)) | Rust/WASM may increase startup payload and retain WASM linear memory in addition to the webview heap; actual cost depends on tree-shaking, loaded code, and workload. Dioxus's own docs estimate a simple web build around 70 KB versus 65 KB for React, but this is not an independently reproducible or feature-matched comparison. The official Tauri scaffolder includes Leptos and Dioxus templates (Dioxus in current changelog); Tauri's Rust frontend guidance includes Leptos. WASM frontends need the Tauri CSP `wasm-unsafe-eval` source. ([Dioxus web](https://dioxuslabs.com/learn/0.7/guides/platforms/web/), [Tauri CSP](https://v2.tauri.app/security/csp/), [scaffolder changelog](https://github.com/tauri-apps/create-tauri-app/blob/dev/CHANGELOG.md)) |

### Shared workload considerations

- **Virtualize messages.** TanStack Virtual supports React, Solid, and Svelte, and documents chat-specific behavior. Keep only visible rows plus overscan mounted; variable-height markdown/code blocks still need measurement and scroll-anchor testing. ([frameworks](https://tanstack.com/virtual/latest/docs/framework), [chat example](https://tanstack.com/virtual/latest/docs/framework/react/examples/chat))
- **Treat streaming cadence as a product decision.** Inference: collect incoming token deltas and publish at a bounded UI cadence (for example, once per animation frame), rather than forcing a framework update per token. Avoid rebuilding/highlighting the entire growing transcript each time; render the active response incrementally and finalize rich markdown when practical. This needs prototype validation.
- **Keep content tooling framework-neutral where possible.** The unified/remark ecosystem parses Markdown into ASTs and supports GFM plugins; Shiki provides TextMate-based highlighting; Monaco includes a browser diff editor; xterm.js is a web terminal with an optional GPU renderer. These are JS/DOM libraries, so they fit naturally in the three JS candidates and can be bridged from WASM with added interop. They can dominate bundle and memory costs, especially Monaco, and should be loaded lazily by feature. ([remark](https://github.com/remarkjs/remark), [Shiki](https://github.com/shikijs/shiki), [Monaco](https://github.com/microsoft/monaco-editor), [xterm.js](https://github.com/xtermjs/xterm.js))
- **Tauri is framework-agnostic.** It packages app assets and uses the platform's system webview; a framework swap does not replace WebView2/WebKitGTK/WKWebView or make web rendering native. Webview version/behavior varies by platform, so benchmark on the intended OS matrix. ([Tauri overview](https://v2.tauri.app/start/), [frontend setup](https://v2.tauri.app/start/frontend/))

## Evidence limits and prototype plan

**Verified:** official docs describe the rendering/state mechanisms and available virtualizer adapters; official Tauri tooling scaffolds the listed frameworks; this checkout has no `package.json`, frontend source, or app benchmark. The repo's current application description and domain vocabulary are in [`GLOSSARY.md`](../../GLOSSARY.md), while the source files present are project instructions/docs only.

**Unknown:** comparative production bundle sizes, peak/steady heap, WASM memory behavior under this workload, token-to-paint latency, virtualized variable-height scroll stability, and T3 Code component reuse. No apples-to-apples benchmark or checked-out T3 Code source was available. Framework vendor performance descriptions are design claims, not measurements for Oxide.

**Prototype gate:** implement the same three-pane shell and scripted transcript in the three candidates; send synthetic token deltas at fixed rates; use 10k mixed-height historical messages with markdown, code, and diff rows; include a long-running active response. Record release bundle size (including actual content tools), cold-start time, peak and post-GC memory, main-thread long tasks/frame drops, update-to-paint latency, and scroll-anchor behavior on each target OS. Add a separate Dioxus/Leptos spike only if the Rust-only frontend advantage justifies the missing shared virtualizer adapters and JS tooling bridge.

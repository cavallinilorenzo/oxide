# How multi-agent tools scope terminals

**Research date:** 2026-10-30 · **Ticket:** [#270](https://github.com/cavallinilorenzo/oxide/issues/270) · **Map:** [#267](https://github.com/cavallinilorenzo/oxide/issues/267)

## Scope

What a terminal is attached to in tools that run several coding agents at once: the conversation, the worktree or checkout, the project, or the window. For each tool: what the terminal belongs to, how many shells exist, what happens to the terminal when the conversation or worktree is deleted, whether the agent's own commands show up in the user's terminal, and how the user tells terminals apart. Then the cost of one PTY plus shell per conversation, and the options for Oxide.

Vocabulary follows [GLOSSARY.md](../../GLOSSARY.md): Project, Thread, Board Thread, Work mode, Surface, Command block. "Checkout" means a working tree: the Project's main checkout or a Board Thread's worktree.

## Answer in one line

Tools that give each agent its own worktree attach terminals to the **workspace (one checkout)**: Conductor, Superset/Paradev, the VS Code Agents window, and in effect Zed. Chat-first tools attach a terminal to **each conversation** but start it in that conversation's checkout: Codex app, Claude Code Desktop, T3 Code. Only Warp shares one shell between the user and the agent, and even Warp keeps the agent's blocks out of the user's block list. Oxide currently does both: the bottom Terminal panel is per Thread and Terminal Work mode is per checkout.

## Oxide today (code reading, `main` at 6839a1e)

- **Bottom Terminal panel: one raw shell per (Project, Thread).** `terminalContextKey(projectId, threadId)` in [`web/src/App.tsx`](../../web/src/App.tsx). Core starts it in `COALESCE(thread.worktree_path, project.path)` ([`crates/oxide-core/src/lib.rs`](../../crates/oxide-core/src/lib.rs), `checkout_path`), so every chat Thread gets a separate shell in the *same* main checkout. The shell is `$SHELL` on macOS/Linux and plain `powershell.exe` on Windows ([`terminal.rs`](../../crates/oxide-core/src/terminal.rs), `shell_command`).
- **Terminal Work mode: one block shell per checkout, not per Thread.** The workbench key is `${projectId}:${worktreePath ? threadId : "main"}`, so every chat Thread shares the main checkout's Command-block shell and each Board Thread has its own. Command history is likewise kept "per checkout" ([docs/workbench.md](../workbench.md)). The map's baseline says both terminals are keyed to (Project, Thread), but only the bottom panel is.
- **Spawned eagerly, never pruned in the UI.** A `TerminalPanel` mounts for every Thread the user selects (`rememberTerminalContext`), and it starts its PTY on mount whether or not the panel is visible. Hiding the panel does not unmount it. `terminalContexts` only grows: `onThreadDeleted` prunes the workbench contexts but not the terminal contexts. A deleted chat Thread's shell therefore keeps running until Oxide quits. For Board Threads, Core's `delete_thread` closes every terminal whose cwd lies inside the worktree before `git worktree remove --force` ([`worktree.rs`](../../crates/oxide-core/src/worktree.rs)), so the worktree case is handled in Core.
- **Agent commands never reach these PTYs.** Providers run their own tool processes. Their commands show up in the Thread as Items (the run Phase of the Activity), not in the user's terminal.
- **Telling terminals apart:** the Terminal Work mode header shows the shell and the current directory. The bottom panel's label is just "Terminal". Two chat Threads in the main checkout show different shells with the same cwd, and nothing on screen distinguishes them.

These points come from reading the source, not from running the app. The leak of a deleted chat Thread's shell is worth confirming with a quick run before anyone acts on it.

### Notes per tool

- **Conductor.** "1 workspace maps to 1 branch … 1 working tree belongs to 1 workspace", and "setup scripts and actions execute from that workspace directory" ([Workspaces and branches](https://www.conductor.build/docs/concepts/workspaces-and-branches)). Its docs encourage "multiple agents in the same workspace when they should share the same branch and code state" ([First workspace](https://www.conductor.build/docs/first-workspace)). The terminal belongs to the workspace, not to a chat. The terminal panel is toggled with ⌘J, with ⌘T/⌘W for new and closed tabs ([Keyboard shortcuts](https://www.conductor.build/docs/reference/keyboard-shortcuts)). Big Terminal Mode is "a full terminal in the center panel" where "terminal sessions restore after restart" ([Big Terminal Mode](https://www.conductor.build/docs/reference/big-terminal-mode)). Processes started by actions get SIGTERM to their process group, then SIGKILL after 5 s ([Scripts](https://www.conductor.build/docs/reference/scripts)). Conductor also captures the user's login-shell environment once per workspace and gives slow rc files a 5 s budget ([Shell configuration](https://www.conductor.build/docs/reference/shells)).
- **Superset / Paradev** (source at [`36c50f9`](https://github.com/ParadevAI/Paradev/tree/36c50f982fdbca8a647faa84f036aa0ee3cdf00b)). "A workspace gives a task its own directory, terminals, and ports" ([Workspaces](https://docs.paradev.com/workspaces)). "Built-in terminal per workspace with multiple tabs and session persistence … Running processes continue" across restarts ([Terminal](https://docs.paradev.com/terminal-integration)). Sessions belong to a `workspaceId`. A detached pty-daemon keeps PTYs alive across host-service restarts, and the renderer calls `terminal.disposeWorkspaceSessions` / `disposeWorktreeSessions` on delete ([`terminal.ts`](https://github.com/ParadevAI/Paradev/blob/36c50f982fdbca8a647faa84f036aa0ee3cdf00b/packages/host-service/src/terminal/terminal.ts), [`dispose-host-sessions.ts`](https://github.com/ParadevAI/Paradev/blob/36c50f982fdbca8a647faa84f036aa0ee3cdf00b/apps/desktop/src/renderer/lib/dispose-host-sessions.ts)). Windows is "not yet available".
- **T3 Code** (source at [`32ecd71`](https://github.com/pingdotgg/t3code/tree/32ecd71726fee16f335484c1f95cbce126d461f6)). The contract keys every terminal call by `threadId` plus a client-chosen `terminalId`, with `cwd` and `worktreePath` ([`contracts/terminal.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/terminal.ts)). The UI caps a split group at 4 terminals ([`types.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/web/src/types.ts)). Archive and delete enqueue `terminal.cleanup`, which runs `close({ threadId, deleteHistory: true })` ([`Orchestrator.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/orchestration-v2/Orchestrator.ts), [`ThreadDeletion.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/orchestration-v2/ThreadDeletion.ts), [`ResourceCleanupService.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/orchestration-v2/ResourceCleanupService.ts)). The server keeps at most 128 inactive (exited) sessions and evicts the oldest; on Windows it starts `powershell.exe -NoLogo` ([`Manager.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/terminal/Manager.ts)). Retention: 5,000 lines / 8 MiB per terminal on the server, 512 KiB in the client ([terminal-runtime.md](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/terminal-runtime.md)). Thread launch runs the project setup script in a thread terminal and closes that terminal if launch is cancelled ([`ThreadLaunchService.ts`](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/orchestration-v2/ThreadLaunchService.ts)). Threads on Local share the project root but still get separate terminals, which is the same model as Oxide's bottom panel.
- **Codex app.** "Each chat in the ChatGPT desktop app includes a terminal scoped to its current project or worktree … ChatGPT can read the current terminal output" ([Integrated terminal](https://learn.chatgpt.com/docs/integrated-terminal)). Chats start on Local or Worktree, and Handoff moves a chat *and its code* between them. Codex-managed worktrees are deleted when "you archive the associated chat" or to stay within a limit, after a snapshot ([Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)). Actions "run within the app's integrated terminal" ([Local environments](https://learn.chatgpt.com/docs/environments/local-environment)).
- **Claude Code Desktop.** "The terminal opens in your session's working directory and shares the same environment as Claude … To open a second terminal tab, click +". Sessions can run in their own worktree under `.claude/worktrees/`, and archiving can discard a worktree's uncommitted changes ([Desktop](https://code.claude.com/docs/en/desktop)).
- **Cursor.** "Cursor runs shell commands directly in your terminal" ([Terminal](https://cursor.com/docs/agent/tools/terminal)). The Agents Window runs "many agents in parallel … locally, in worktrees, in the cloud, and on remote SSH" ([Agents Window](https://cursor.com/docs/agent/agents-window), [3.0 changelog](https://cursor.com/changelog/3-0)). It keeps at most 25 worktrees per machine by default ([Worktrees](https://cursor.com/docs/configuration/worktrees)). Its docs do not say how terminals are scoped in the Agents Window.
- **VS Code.** In the Agents window, "only one session pane is active at a time … direct the Files, Changes, Terminal, Tasks, and browser actions to that session", and Terminal and Tasks are "commands and tasks that run in the session's workspace folder or worktree". It also warns that "separate conversations don't isolate files: sessions using the same folder can edit the same files" ([Agents window](https://code.visualstudio.com/docs/agents/run/agents-window)). For the Local harness: "Background terminals that you have not revealed are automatically cleaned up when their command finishes", and `chat.tools.terminal.outputLocation` picks between chat and the integrated terminal ([Tools](https://code.visualstudio.com/docs/agents/run/tools), [AI settings](https://code.visualstudio.com/docs/agents/reference/ai-settings)). Persistent sessions reconnect on reload and revive on restart ([Terminal advanced](https://code.visualstudio.com/docs/terminal/advanced)). Each tab has a "name, icon, color, and group decoration" ([Terminal basics](https://code.visualstudio.com/docs/terminal/basics)).
- **Zed.** The Terminal Panel is docked per workspace and can have several tabs ([Terminal](https://zed.dev/docs/terminal)). The built-in agent's `terminal` tool "executes shell commands … creating a new shell process for each invocation" ([Tools](https://zed.dev/docs/ai/tools)). Terminal Threads "run the native command-line tool in a terminal that Zed organizes as a thread" and "are closed rather than archived" ([Terminal Threads](https://zed.dev/docs/ai/terminal-threads)). For worktrees: "moving the thread to Thread History saves the worktree's Git state and removes it from disk" when no other active thread uses it ([Parallel Agents](https://zed.dev/docs/ai/parallel-agents)).
- **Warp.** A "terminal session" and an "agent conversation" are separate concepts. "Terminal blocks … always appear in your terminal block list … Agent conversation blocks — commands executed within an agent conversation (either by you or the agent) — only appear within that specific conversation." In Full Terminal Use, "the shell stays open, and you can type directly into the same session". A new tab or pane starts a new conversation ([Terminal and Agent modes, Full terminal use](https://docs.warp.dev/agents/local-agents/interacting-with-agents/terminal-and-agent-modes/)). Worktrees open "in a new Warp tab or pane" ([Git worktrees](https://docs.warp.dev/code/git-worktrees/)).

### Patterns

1. **The real unit is the checkout.** Tools built around worktrees give one terminal set per workspace and let several chats share it (Conductor, Superset, the VS Code Agents window). Chat-first tools give one terminal per conversation but always start it in that conversation's checkout. No tool gives a single terminal a cwd that changes as the user switches between worktrees.
2. **Tabs inside the scope.** Every tool that has a scoped terminal (except the Codex docs, which don't say) offers several tabs or splits inside that scope. One shell per scope is never the ceiling.
3. **Agent commands stay out of the user's shell.** The only exceptions are tools where the agent *is* a terminal program (Superset, Zed Terminal Threads, Conductor presets) and Warp, where the shell is shared but the blocks are partitioned. The common bridge goes the other way: the agent can *read* the user's terminal (Codex app, T3 excerpts, Zed "add selection to thread", Warp attached blocks).
4. **The terminal dies with its worktree.** Wherever cleanup is visible (T3, Superset, Oxide's Core for Board Threads), deleting or archiving the owner closes its terminals. Most docs don't spell this out.
5. **Persistence across restarts** is common: Conductor, Superset (daemon), VS Code, T3 (history only). Oxide's output is session-only by design ([workbench.md](../workbench.md)).

## Cost of one PTY plus shell per conversation

**Processes.** On macOS and Linux a terminal is one shell process (plus whatever it runs). On Windows, ConPTY adds a console host per pseudoconsole: `CreatePseudoConsole` results in "Windows … spin[ning] up a ConHost instance connected to the other end of the pipes", and "closing the ConPTY will terminate the associated ConHost and any attached clients" ([Microsoft, Introducing ConPTY, 2018](https://devblogs.microsoft.com/commandline/windows-command-line-introducing-the-windows-pseudo-console-conpty/)). Oxide's `portable-pty` 0.9.0 calls `kernel32` `CreatePseudoConsole`, or a sideloaded `conpty.dll` plus OpenConsole if one is shipped (`src/win/psuedocon.rs`). **So each Oxide terminal on Windows is two processes, `conhost.exe` and `powershell.exe`.**

**Startup on Windows.** The PowerShell team measured `pwsh -noprofile -command 1` at an average of **1,176 ms** over 100 runs. A profile added about 290 ms in their example, and deferring interactive-only work brought that down to 217 ms. A commenter measured **1,859 ms** for interactive startup without a profile, against 519 ms non-interactive ([Steve Lee, Optimizing your $Profile, 2021](https://devblogs.microsoft.com/powershell/optimizing-your-profile/)). Neither figure states the hardware, and both are PowerShell 7. Oxide starts **Windows PowerShell 5.1** (`powershell.exe`) **without `-NoProfile`**: the bottom panel with no arguments at all, Terminal mode with `-NoLogo -NoExit`. The user's profile is therefore on the critical path for every new terminal. VS Code's docs also warn about "a heavy PowerShell startup script" ([Terminal profiles](https://code.visualstudio.com/docs/terminal/profiles)).

**Memory.** I found no primary source giving a working-set figure for an idle `powershell.exe` or `conhost.exe`. It has to be measured (see below).

**Local measurement (macOS 27.0.1, Apple M1; not Windows).** I spawned 10 shells per row under a PTY with Python's `pty.fork` and timed spawn to first output byte. Resident memory is the shell's own RSS 1 s later.

| Shell | First output, median (min to max) | RSS per shell, median |
|---|---|---|
| `/bin/bash --noprofile --norc -i` (close to Oxide's macOS block shell) | 15 ms (7 to 30) | 2.7 MiB |
| `/bin/zsh -i` with this user's rc files (close to the bottom panel's `$SHELL`) | 859 ms (758 to 1,314) | 5.5 MiB |
| `/bin/zsh -il` | 1,005 ms (990 to 1,176) | 5.5 MiB |

On POSIX the shell process itself is cheap; startup is dominated by the user's rc files. RSS counts shared pages, so these figures overstate the marginal cost. The script lives outside the repo and is not part of Oxide.

**What this means for Oxide's multiplier.** Today Oxide opens one bottom-panel shell for every Thread the user *visits*, whether or not the panel is shown, plus one block shell per checkout opened in Terminal mode. A user who visits 10 Threads in a session holds about 10 to 12 shells. On Windows that doubles to 20 to 24 processes, each with a PowerShell profile load the user may never use. Scoping per checkout bounds the count at 1 + the number of Board Threads with an open terminal. Spawning lazily (on first open) bounds it at what the user actually opened.

**To measure on Windows (the primary platform):** with the release build, open the bottom panel on N Threads. Record the time from `startTerminal` to the first PTY byte and to the first prompt, and the private working set of each `powershell.exe` and `conhost.exe` (`Get-Process powershell,conhost | Select Id,WS,PM`). Run once with the user's profile and once with `-NoProfile`.

## Options for Oxide

| Option | What it means | For | Against |
|---|---|---|---|
| **A. Per Thread (keep the bottom panel's model)** | Each Thread has its own terminal(s) in its checkout. Like Codex app, Claude Code Desktop, T3 Code. | The terminal travels with the conversation, so switching Thread switches context. Deleting a Thread has an obvious owner to clean up. Per-Thread scrollback is useful for a Turn's follow-up. | Chat Threads share the main checkout, so N shells point at one folder: two `npm run dev` in two Threads collide on ports and files, and a dev server "disappears" when the user switches to another chat Thread on the same checkout. It costs the most processes (×2 on Windows). It disagrees with Terminal Work mode, which is already per checkout. Needs a label, since cwd alone doesn't identify the terminal. |
| **B. Per checkout (recommended)** | One terminal set for the main checkout, shared by all chat Threads; one set per Board Thread's worktree. Both the bottom panel and Terminal Work mode use the same key. Like Conductor, Superset and the VS Code Agents window. | Matches where commands actually run. A dev server keeps running and stays visible across chat-Thread switches. The process count is bounded and small. It unifies the two terminals Oxide has today (the panel and the mode can share a shell, as T3's and Conductor's centre terminals do). Core already closes a worktree's terminals when its Board Thread is deleted. It lines up with Diff scope defaults (Board Threads are reviewed per branch). | A chat Thread no longer owns "its" terminal; the scrollback mixes everything the user ran in the main checkout. Deleting a chat Thread cleans nothing, so the main checkout's terminals need an explicit close. Selecting a Board Thread still switches terminals, so the header must say which checkout is shown. |
| **C. Per Project or window, single terminal** | One shell per Project (VS Code classic, Zed panel) that the user `cd`s around. | Cheapest; one place to look. | Board Threads exist to isolate worktrees, and a shared shell invites running tests in the wrong checkout. No tool built around parallel worktrees does this. |
| **D. B plus tabs and ownership labels** | Per checkout, with tabs inside each set. A tab opened from a Thread (or by a Setup command) is labelled with that Thread's title; it does not move when the user switches Thread. | Keeps B's bounded cost and adds the "which Thread was this for" cue that A provides. It mirrors Conductor and Superset tabs and T3's setup-script terminal. It makes running the Setup command visible without a new Surface. | More UI: a tab strip in both the panel and the mode, close and rename handling. Ownership labels need a rule for what happens when their Thread is deleted (keep the tab, drop the label). |

Whichever option is chosen, three fixes follow from the code reading:

1. **Spawn on first open, not on mount.** Today a hidden panel still starts a shell for every visited Thread. On Windows each one is two processes plus a PowerShell profile load.
2. **Close a deleted Thread's terminals** on the web side as well. Today `terminalContexts` is never pruned, so a deleted chat Thread's shell lives until Oxide quits.
3. **Label the terminal with its scope** (checkout or worktree name and branch, plus the owning Thread for tabs under D). Every tool reviewed shows at least a tab title. Oxide's bottom panel shows only "Terminal".

**Researched opinion:** B, growing into D. It is the model every worktree-first tool converged on, it bounds the process cost on the Windows-primary platform, and it removes the existing split between the panel (per Thread) and Terminal Work mode (per checkout). The cost is losing per-chat-Thread scrollback, which the Thread's own Activity already covers for the agent's commands. A prototype should test whether users miss per-Thread terminals when two chat Threads share the main checkout.

## Evidence limits

- **Closed-source tools** (Conductor, Codex app, Claude Code Desktop, Cursor) are described from their official docs and changelogs only. Where a doc is silent (terminal fate on archive, scoping in Cursor's Agents Window, terminal tabs in the Codex app), the table says "not documented" and makes no inference.
- **Superset/Paradev and T3 Code** were read at the pinned commits above. They move fast; UI behaviour, such as exactly when T3 spawns a hidden thread's PTY, was not run.
- **Oxide** findings come from reading `main` at 6839a1e, not from running the app. Confirm the deleted-Thread shell leak before fixing it.
- **Windows costs** come from one PowerShell team post (PowerShell 7, hardware not stated) and Microsoft's ConPTY architecture post. There is no primary memory figure, and nothing measured for Windows PowerShell 5.1, which is what Oxide launches. The macOS figures are a **local measurement** on one machine with one user's rc files and are not representative of Windows.
- `references/` submodules are declared in `.gitmodules` but not recorded in the tree at 6839a1e. T3 Code and Paradev sources were fetched from GitHub at the commits cited.
